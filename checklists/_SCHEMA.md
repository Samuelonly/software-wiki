# `checklists/` 字段定义

一个软件品类一个文件。下面是必须字段和填写规则——写新清单之前先读这个。

## 文件头

```yaml
---
category: archive-utility     # 品类 id，与文件名一致
version: V1
updated: 2026-11-24
items: 0                      # 条目数，按实际写
status: 草稿                   # 草稿 / 已过老手评审 / 已验证
reviewers: []                 # 过评审的人，写名字；没过就空着
---
```

- `status` 三个值：
  - **草稿**：自己写的，没找人过
  - **已过老手评审**：找做过这类软件的人逐条过过
  - **已验证**：拿真项目跑过，条目确实能捞出问题
- **没过老手评审的清单不能当验收依据用**——草稿就是草稿，别冒充资产。

## 每条验收项的格式

```markdown
- [ ] **一句话标题**（这条要验什么本事）
  - 验法：一句话怎么验完（外行照着念能判，不用看代码）
  - 来源：从哪次真实的坑里来的 / 谁提的
```

一条合格的验收项，三条标准（缺一不收）：

1. **描述"应具备什么能力"，不描述"如何实现"**
   - ✅ "原文件不能被删除"
   - ❌ "用 copy-then-delete 模式"
2. **一句话能验证，无需阅读代码**
   - ✅ "压一个文件，压完原文件是否还在"
   - ❌ "检查文件处理逻辑是否遵守了不可变原则"
3. **用户确实关心，但买家不易想到要问**
   - ✅ "备份文件是否同步更新"
   - ❌ "能打开压缩文件"（属于基本预期，无需单列）

## 铁律

1. 条数因品类而异，**不应为追求数量而添加**。压缩软件可能很多，其他品类可能只有五条。
2. 不确定的条目宁可不写；写入的条目必须可验证。
3. 每条带来源——记录其来自哪次真实问题。没有来源的标"推断"。
4. 写完后请三位有该类软件开发经验的人评审一遍，把 `status` 从"草稿"改掉。这一步未完成，这份清单尚不成立。
5. 清单是**外挂**的：它描述"这一品类应具备哪些能力"，而非"这个项目计划里有哪些任务"。不应将其写成任务列表。
