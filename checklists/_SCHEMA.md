# `checklists/` 字段定义

一个软件品类一个文件。下面是必须字段和填写规则——写新清单之前先读这个。

## 文件头

```yaml
---
category: archive-utility     # 品类 id，与文件名一致
version: V1
updated: 2026-11-24
items: 0                      # 条目数，按实际写
status: 草稿                   # 草稿 / 已过老手评审 / 已验证
reviewers: []                 # 过评审的人，写名字；没过就空着
---
```

- `status` 三个值：
  - **草稿**：自己写的，没找人过
  - **已过老手评审**：找做过这类软件的人逐条过过
  - **已验证**：拿真项目跑过，条目确实能捞出问题
- **没过老手评审的清单不能当验收依据用**——草稿就是草稿，别冒充资产。

## 每条验收项的格式

```markdown
- [ ] **一句话标题**（这条要验什么本事）
  - 验法：一句话怎么验完（外行照着念能判，不用看代码）
  - 来源：从哪次真实的坑里来的 / 谁提的
```

一条合格的验收项，三条标准（缺一不收）：

1. **说"该有什么本事"，不说"怎么实现"**
   - ✅ "原文件不能被删"
   - ❌ "用 copy-then-delete 模式"
2. **一句话能验完，不用看代码**
   - ✅ "压一个文件，压完原文件还在不在"
   - ❌ "检查文件处理逻辑是否遵守了不可变原则"
3. **用户真在乎，但买家想不到要问**
   - ✅ "改了 backup 没"
   - ❌ "能打开压缩文件"（谁都想得到，不值得占一条）

## 铁律

1. 条数因品类而异，**别凑数**。压缩软件可能很多，别的可能就五条。
2. 不确定的条目宁可不写；写了就得能验。
3. 每条带来源——从哪次真实的坑里来的。没来源的标"推断"。
4. 写完去找三个做过这类软件的人过一遍，把 `status` 从"草稿"改掉。这一步没做，这份清单就还不成立。
5. 清单是**外挂**的：它是"这品类该有哪些本事"，不是"这个项目计划里有哪些任务"。别把它写成任务列表。
