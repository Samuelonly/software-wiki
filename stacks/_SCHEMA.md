# `stacks/` 字段定义

一个技术块一个文件。下面是必须字段和填写规则——填新块之前先读这个。

## 文件头（每个文件必须有）

```yaml
---
block: web-frontend          # 技术块 id，与文件名一致
version: V1                  # 本条目的版本
updated: 2026-11-24
source:                      # 来源，可多个
  - name: VibeStart
    repo: https://github.com/VinkyDev/vibestart
    commit: 8565902dfdd3d1d2530a46f8051cd038bfba7d04   # 锁定，不跟随上游更新
    license: MIT
verification: 实测            # 只能填 实测 / 文档 / 未验证
---
```

- `verification` 三个值的含义：
  - **实测**：来源方在 CI 里真装、真测、真构建过，且有公开记录（CI badge / verification 分支等）。必须有 `source.commit`。
  - **文档**：只在文档里这么写，没有可查的实测记录。
  - **未验证**：连文档依据都没有，只是常识或经验判断。
- 找不到实测来源就标 `文档`，**不得冒充 `实测`**。标 `实测` 必须有 commit。

## 正文结构（按顺序）

### 1. 一句话定位
用一句话说明这个技术块的用途。

### 2. fit —— 适合什么场景
什么情况下选这一块的这些技术。写成可以对照自己项目的条件，不要写成广告词。

### 3. 覆盖清单 —— 有哪些选项
用表格列：层级 / 可选项 / 备注。只写来源里真实存在的，不凭空补充。

### 4. 不覆盖 —— 明确没有什么
**这一节最重要。** 列出这个来源明确不支持的平台/语言/框架。
「它没做」和「它做了但做得差」要分开写——前者是这个库的空位，等着别人填。

### 5. gotchas —— 已知问题
每条坑写清楚：什么情况下踩、症状是什么、怎么绕。
区分两种：
- **来源明说的**（原文有依据）
- **推断的**（我们的判断，需标注，不与事实混用）

### 6. 验证依据
`实测` 的贴出来源方的 CI / verification 链接和原文说法；`文档` / `未验证` 的写明依据是什么。

### 7. 待核实
来源里没说清、或者数字对不上的地方，单列一节，不为来源补台。

## 铁律

1. 只写来源里真实存在的技术，不为了追求完整而凭空补充。
2. 每条事实带出处（来源名 + commit）。推断的明确标"推断"。
3. 数字对不上就记进「待核实」，不自行修正。
4. 一个技术块一个文件，不混用平台。
